Docker na VM

0:00 / 0:00

A primeira peça real do campo de treino: instalar o Docker dentro da VM Ubuntu e liberar o uso sem sudo. O critério do passo é pequeno de propósito: docker ps respondendo sem sudo. No caminho, o imprevisto que virou aula: a VM inteira congelou, e a causa não era o que parecia.

Instalar o Docker — o script oficial +

Um comando só. O curl baixa o script oficial de instalação e o pipe entrega direto pro shell rodar com sudo. O script detecta a distribuição, adiciona o repositório certo e instala o Docker Engine completo:

curl -fsSL https://get.docker.com | sudo sh

Detalhe do dia a dia que aconteceu de verdade: o sudo pede senha e bateu a dúvida "qual senha eu coloquei nessa VM?". A resposta que salva: no Ubuntu, a senha do sudo é a mesma senha do login. Se você acabou de logar digitando uma senha, é essa.

Docker sem sudo — o grupo docker +

Recém instalado, o Docker só obedece root. Pra usar com o usuário normal, entra no grupo docker que o instalador criou (grupo, no Linux, é uma lista de usuários com uma permissão em comum):

sudo usermod -aG docker $USER

Pegadinha clássica: o comando não vale na hora. A lista de grupos do usuário é carregada no login, então precisa sair do SSH e entrar de novo. Depois de relogar, o critério do passo:

docker ps
# CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES

Tabelinha vazia, sem erro de permissão: Docker instalado e liberado.

O travamento — soft lockup e a falsa pista de OOM +

Na hora de conferir, o docker ps ficou pendurado sem resposta e o Ctrl+C não voltava. O teste esperto do diagnóstico: rodar um comando bobo, tipo ls. Ele respondeu na hora, o que separa o problema: terminal vivo, serviço do Docker travado. Depois nem o sudo respondia, e a sessão congelou de vez.

Na tela da própria VM, o kernel gritava:

rcu: rcu_preempt kthread starved for 20295 jiffies!
rcu: Unless rcu_preempt kthread gets sufficient CPU time, OOM is now expected behavior.
watchdog: BUG: soft lockup - CPU#4 stuck for 59s! [dockerd:2176]
watchdog: BUG: soft lockup - CPU#6 stuck for 59s! [swapper/6:0]

Primeira leitura: faltou memória (o "OOM" na mensagem). Leitura errada. A VM tinha 8 GB de RAM e 8 CPUs, folga de sobra. A linha do OOM era consequência, não causa. A causa real estava no CPU stuck: as CPUs virtuais ficaram sem tempo de processador de verdade.

O diagnóstico — VirtualBox por cima do Hyper-V +

A pista final foi o ícone de tartaruga 🐢 no canto inferior da janela do VirtualBox. Tartaruga significa: o VirtualBox não está rodando direto no processador. No Windows 11, quando o Hyper-V da Microsoft está ativo (e ele vem ativo por causa de recursos de segurança, do WSL 2 e do Docker Desktop), o VirtualBox é obrigado a rodar por cima dessa camada: funciona, mas mais lento e sujeito a travadas sob carga.

Desligar o Hyper-V devolveria o modo rápido, mas quebraria o WSL 2 e o Docker Desktop do próprio Windows, usados no dia a dia. Não compensa pra uma VM de treino.

A solução pragmática: reduzir as CPUs da VM de 8 pra 4 (Settings → System → Processor). Por que menos CPU ajuda: cada vCPU é uma promessa de processador que o VirtualBox faz pro Linux convidado, e o kernel vigia se todas estão andando. Com 8 promessas, o Windows precisa achar espaço pra 8 threads ao mesmo tempo, e com a camada do Hyper-V no meio alguma sempre fica pra trás. Com 4, escalonar fica fácil e ninguém fica sem vez. Pra Ubuntu + Docker + containers leves, 4 sobra.
