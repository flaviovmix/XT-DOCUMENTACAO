Réplica da Stack

0:00 / 0:00

A miniatura da arquitetura do servidor real, montada dentro da VM: uma rede interna do Docker, um container nginx por site (sem porta pra rua) e o Caddy na frente como única entrada. No fim, dois sites respondendo no navegador do Windows e os dois gestos do dia a dia treinados: trocar conteúdo e adicionar site novo com reload a quente.

A rede interna — containers que se chamam pelo nome +

Uma rede do Docker é um espaço onde os containers se enxergam pelo nome. Dentro da rede web, o Caddy chama o container meusite pelo nome, sem IP nenhum. É a mesma rede, com o mesmo nome, que existe no servidor remoto:

docker network create web
O primeiro site — nginx com volume espelho +

Primeiro o conteúdo (uma pasta com um index.html), depois o container que serve essa pasta:

mkdir -p ~/meusite
echo '<h1>Funciona! site local</h1>' > ~/meusite/index.html

docker run -d --name meusite --network web --restart unless-stopped \
  -v ~/meusite:/usr/share/nginx/html:ro nginx:alpine
FlagO que faz
-dRoda em segundo plano
--name meusiteO nome que a rede vai conhecer
--network webPõe o container na rede interna
--restart unless-stoppedReliga sozinho se a VM reiniciar
-v pasta:/usr/share/nginx/html:roEspelha a pasta da VM dentro do container (só leitura)

Detalhe importante: não tem -p nesse comando. O site não tem porta pra rua, ele só existe dentro da rede web. E o --restart unless-stopped já se pagou: quando a VM reiniciou depois do travamento, o container voltou sozinho.

O Caddy na frente — porteiro único na porta 80 +

O Caddy é o porteiro: o único container com porta aberta pra fora. A configuração é o Caddyfile, um bloco por site: "quem chegar pedindo meusite.local, encaminha pro container meusite na porta 80".

mkdir -p ~/caddy
cat > ~/caddy/Caddyfile << 'EOF'
http://meusite.local {
    reverse_proxy meusite:80
}
EOF

docker run -d --name caddy --network web --restart unless-stopped \
  -p 80:80 \
  -v ~/caddy/Caddyfile:/etc/caddy/Caddyfile:ro \
  caddy:latest

A novidade é o -p 80:80: abre a porta 80 da VM e entrega pro Caddy. Ele é o único de cara pra rua; os nginx dos sites ficam escondidos atrás, alcançáveis só por dentro da rede.

Ensinar o Windows — o arquivo hosts +

meusite.local não existe na internet. Antes de perguntar pro DNS, o navegador consulta a "agenda de contatos" local do Windows: o arquivo hosts. Num PowerShell como administrador:

Add-Content C:\Windows\System32\drivers\etc\hosts "192.168.56.101  meusite.local"

Abrindo http://meusite.local no navegador: "Funciona! site local". O aviso de "não seguro" é normal e esperado: ambiente local não tem certificado. HTTPS com cadeado é assunto do servidor real, onde o Caddy consegue certificado sozinho.

Gesto 1 — trocar o conteúdo (sem restart) +

O gesto de atualizar um site que já está no ar:

echo '<h1>mudei o conteudo</h1>' > ~/meusite/index.html
# recarrega o navegador: mudou

Sem restart, sem reload, sem rebuild. O volume é um espelho: o container não guarda cópia dos arquivos, ele enxerga a pasta da VM em tempo real.

Gesto 2 — adicionar um site novo (reload a quente) +

O padrão do servidor: cada site novo = um container nginx novo + um bloco novo no Caddyfile.

mkdir -p ~/site2
echo '<h1>site 2</h1>' > ~/site2/index.html

docker run -d --name site2 --network web --restart unless-stopped \
  -v ~/site2:/usr/share/nginx/html:ro nginx:alpine

cat >> ~/caddy/Caddyfile << 'EOF'

http://site2.local {
    reverse_proxy site2:80
}
EOF

Detalhe de shell que importa: acrescentar no fim usa >> (dois sinais). Um > sozinho sobrescreveria o arquivo inteiro e apagaria o site 1.

E o comando-chave, que recarrega a configuração a quente, sem derrubar o site 1:

docker exec caddy caddy reload --config /etc/caddy/Caddyfile

Linha nova no hosts do Windows pro site2.local, e os dois sites respondem no navegador.

No servidor real +

Essa miniatura é exatamente o fluxo do servidor remoto: um nginx por site, Caddy único na frente, e os dois gestos (trocar arquivo, adicionar site + reload) são os mesmos. As únicas diferenças do lado real:

  • O domínio é de verdade, apontado por DNS (não por arquivo hosts)
  • O HTTPS é automático: o Caddy consegue e renova o certificado sozinho

Com isso a fila da prática local fechou: o campo de treino está completo e idêntico ao servidor real em miniatura. Próximos passos possíveis: Postgres em container com volume persistente, backup e restauração, e o acesso ao servidor de verdade.
